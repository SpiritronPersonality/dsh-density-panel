## 0. 修正后的结论

v24 把两类文本分开处理，结果从"一律抽样成指针"变成：

| 文本类型 | v23 | v24 | 判决 |
|---|---|---|---|
| 中文长散文 | 压到 2.12%，细节 0/24 | **不压缩**（原样保留） | 正确：宁可不省，不丢内容 |
| 大型源码 | 压到 0.71%，定义 0/24 | `code-outline` 保留 14.9%，**函数定义 24/24** | 结构完整，实现体走召回 |

也就是说：**散文不再被破坏，代码保住全部结构**。代码的具体实现（函数体）仍然被省略，需要时召回。

## 1. 测试设计（三层 + 两套指标）

## 6. 代价与边界

- 散文不压缩 ⇒ 中文长文**零节省**。这是刻意选择：抽样式压缩对叙事等于丢弃。
- 代码只留声明 ⇒ 问"这个函数怎么实现"仍需召回；问"在哪、签名是什么"可直接回答。
- 召回成本 ≈ 原文大小，高频召回会抵消节省。
- 质量仍无 A/B（任务通过率未测）。

## 9. v25：离线通过、线上没通过的差异

v24 的离线测试全绿，但**线上第一次读内核源码仍走了 `headtail`**（影子日志：`method=headtail`，3382→202 token）。原因是 `read` 工具的输出每行带 `3000: ` 行号前缀，代码特征（行首 `#`、行尾 `;`）全被打断，`codeOutline` 的代码占比检测判定失败。

修复：分类前先剥离 `^\s*\d+:\s?` 前缀（`stripGutter`），输出仍保留行号。

| 检查 | 结果 |
|---|---|
| 400 行带行号的内核代码（13,309 字符） | `code-outline`，保留 **10.5%**，函数定义 **9/9** |
| 同一批语料（原始无行号） | 不变：14.9% / 24-24 |
| v24 线上读散文（红楼梦 120 行） | **未被压缩**（P2 生效，原样返回） |

这正是"离线测试通过 ≠ 生产链路通过"的典型案例：测试喂的是原始文件，真实链路喂的是工具格式化后的输出。教训已写进测试工具的注释里。

## 10. 版本与测试

## 11. v25 线上验证与 v26 打磨

v25 重启后，线上读 400 行内核代码返回：

```
3005: static int affine_move_task(struct rq *rq, struct task_struct *p, ...)
3158: static int __set_cpus_allowed_ptr_locked(struct task_struct *p, ...)
3243: int __set_cpus_allowed_ptr(struct task_struct *p, struct affinity_context *ctx)
3385: #ifdef CONFIG_SMP
… 378 行实现省略（保留声明与签名）…
```

方法确认为 `code-outline`，不再是 `headtail`。但暴露两个瑕疵：函数体内的局部 `struct ... = NULL;` 被当成声明保留；`/*` 被路径正则当成事实，产生一行无意义的 `[硬事实 1 条] /*`。

v26 修复后同一段：保留 **7.0%**、**0 条伪事实**、无噪声行。属于打磨，不改变结论。
